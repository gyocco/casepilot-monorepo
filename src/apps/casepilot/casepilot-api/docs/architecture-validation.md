# Validación automatizada de arquitectura de CasePilot API

- Estado: implementada para esta API.
- Fecha: 2026-10-01.
- Revisión: 2026-10-03.
- Normativa: [catálogo BCK vigente](../../../../../docs/architecture/backend-architecture-baseline-rules.md), adoptado por la [arquitectura particular de CasePilot](../../../../../docs/architecture/casepilot-backend-architecture.md).
- Decisión de herramientas y convenciones verificables: [ADR 0007](../../../../../docs/adr/0007-automated-api-architecture-validation.md).
- Organización vigente y evolución de BCK-009/BCK-014/BCK-017: [ADR 0008](../../../../../docs/adr/0008-application-wide-backend-layers.md).
- Organización de Application por recurso, regla particular [CPA-001](../../../../../docs/architecture/casepilot-backend-architecture.md#cpa-001--application-de-la-api-organizada-por-recurso): [ADR 0009](../../../../../docs/adr/0009-resource-organized-application.md).
- Trío obligatorio por operación y shared por recurso, [BCK-023](../../../../../docs/architecture/backend-architecture-baseline-rules.md#bck-023--application-organizada-por-recurso-y-operacion): [ADR 0017](../../../../../docs/adr/0017-operation-organized-application.md).

- Contratos CQRS, herencia y nomenclatura de handlers, regla particular [CPA-002](../../../../../docs/architecture/casepilot-backend-architecture.md#cpa-002--contratos-cqrs-compartidos-e-invocacion-directa): [ADR 0010](../../../../../docs/adr/0010-shared-cqrs-contracts.md).
- Presentation por módulo de recurso y separación composición/transporte, regla particular [CPA-004](../../../../../docs/architecture/casepilot-backend-architecture.md#cpa-004--presentation-organizada-por-modulo-de-recurso): [ADR 0014](../../../../../docs/adr/0014-resource-organized-presentation.md).

Este documento describe la cobertura ejecutable; no reemplaza el catálogo ni convierte un check verde en evidencia de cumplimiento completo. Las herramientas son dependencias de desarrollo del paquete API y no se importan desde el producto.

## Comandos

Requisitos: dependencias instaladas con `pnpm install --frozen-lockfile`. Los scripts de la API que necesitan tipos construyen primero `@casepilot/cqrs`, `@casepilot/abstractions` y `@casepilot/exception-handler`, consumiendo sus declaraciones ESM del workspace. Verificado con Node.js 22.12.0 y pnpm 10.13.1. Los checks estáticos y sus pruebas no necesitan Docker, PostgreSQL, archivos `.env` ni una API en ejecución.

Desde la raíz del monorepo:

```bash
pnpm check:api:architecture
pnpm test:api:architecture
```

Desde `src/apps/casepilot/casepilot-api/`:

```bash
pnpm check:architecture
pnpm test:architecture
```

`check:architecture` ejecuta secuencialmente **type-check → ESLint → dependency-cruiser → ts-morph** y termina con código distinto de cero ante el primer fallo. Este es el comando completo que debe usarse como gate local o en CI: el compilador nativo verifica los tipos y caminos de retorno con la configuración NodeNext del proyecto, y los otros mecanismos agregan restricciones arquitectónicas.

Para diagnosticar un mecanismo por separado, desde la API:

| Comando | Alcance |
| --- | --- |
| `pnpm typecheck` | Fuentes, tests, herramientas y configuraciones; sin emitir archivos. |
| `pnpm lint` | ESLint con tipos y reglas arquitectónicas; cero warnings permitidos. |
| `pnpm check:dependencies` | Grafo de imports/exports alcanzable desde todo `src/`. |
| `pnpm check:structure` | Ubicación de capas/database, agrupación por recurso/operación, trío handler/request/response y sus símbolos, módulo de Presentation propietario, firmas, retornos y llamadas directas a handlers. Rechaza una selección vacía de fuentes Application. No sustituye `typecheck`. |
| `pnpm test:architecture` | Pruebas de los tres mecanismos con ejemplos válidos e inválidos. |

`pnpm test:api` también ejecuta estas pruebas después de las unitarias existentes. Los builds y endpoints continúan verificándose con `pnpm build:api` y `pnpm test:api:integration`; únicamente integración necesita Docker y PostgreSQL efímero de Testcontainers. No se incorpora un workflow remoto: cualquier pipeline puede invocar estos mismos comandos después de instalar el lockfile.

## Responsabilidad de cada mecanismo

### VS Code y lint con tipos

La [configuración compartida del editor](../../../../../.vscode/settings.json) utiliza flat config y selecciona el directorio de cada paquete con `eslint.workingDirectories`, igual que los scripts `pnpm --dir`. Ofrece el TypeScript 5.9.3 instalado en la API: selecciona **TypeScript: Select TypeScript Version → Use Workspace Version** si el editor todavía usa su versión integrada. No configura reglas alternativas ni desactiva `no-unsafe-*`.

Las fuentes `src/**/*.ts` de API, CQRS, abstractions y exception-handler usan `parserOptions.projectService: true` con el `tsconfig.json` más cercano, el mismo proyecto de fuentes que utiliza VS Code. Tests, herramientas y archivos de configuración conservan los proyectos explícitos `tsconfig.json`/`tsconfig.test.json`: esos archivos no están incluidos en el proyecto de build y siguen teniendo lint con tipos, sin ampliar `allowDefaultProject` ni excluirlos del gate.

Los paquetes compartidos exportan `dist/*.d.ts` y ESM construidos. VS Code no ejecuta el paso previo de build que sí realizan los scripts. Después de instalar dependencias, desde la raíz:

```bash
pnpm build:contracts
```

Cuando se editan librerías, `pnpm watch:contracts` realiza ese build inicial en orden de dependencias y después vigila los tres paquetes con TypeScript. Los artefactos permanecen ignorados por Git. Detén el watch con Ctrl+C antes de ejecutar los gates, que también escriben esos artefactos.

Un mensaje `Unsafe call/construction of a type that could not be resolved` significa que TypeScript no pudo resolver el tipo utilizado por la regla. Comprueba el import y los errores de compilación con `pnpm typecheck:api`. Si los checks pasan pero el editor conserva ese diagnóstico después de cambios entre archivos o reconstrucciones, ejecuta **ESLint: Restart ESLint Server**; para diagnósticos propios de TypeScript, **TypeScript: Restart TS Server**. typescript-eslint [documenta la limitación de diagnósticos entre archivos](https://typescript-eslint.io/troubleshooting/typed-linting/#editor-eslint-reports-become-out-of-date-after-file-changes): `projectService` alinea la selección de proyectos, pero no garantiza que la extensión vuelva a analizar automáticamente cada consumidor.

Las pruebas sintácticas de arquitectura utilizan `disableTypeChecked` únicamente para snippets ficticios sin proyecto TypeScript. No acreditan `no-unsafe-call` ni sustituyen `pnpm lint:api`. [eslint.test.ts](../test/architecture/eslint.test.ts) también ejecuta la configuración real, con tipos activos, sobre los responses/handler Health y comprueba que llamadas, construcciones y bases con imports irresolubles sí produzcan errores `no-unsafe-call`, sin errores fatales de parser. Estas regresiones son parte de `test:api:architecture` y `test:api`; no simulan la sesión ni las cachés internas de VS Code.

### ESLint

[eslint.config.mjs](../eslint.config.mjs) mantiene `recommendedTypeChecked`, imports restringidos en Domain/Application/Presentation y las reglas generales de calidad de TypeScript. Agrega detección de:

- Uso directo de `process` y `fetch` en Domain/Application.
- CPA-002: imports/reexports nombrados de `Handler` como tipos, permitiendo las bases runtime `Request`/`Response`; rechazo de imports/reexports privados de CQRS por paquete o ruta relativa.
- Llamadas a `transaction`, `startTransaction`, `commitTransaction` y `rollbackTransaction` desde repositorios, mediante miembros ordinarios o literales computados.
- Llamadas ordinarias o computadas literales a `findAndCount` y `findAndCountBy` en repositorios, incluidos archivos `.repository.ts` de Infrastructure.
- CPA-003: entradas públicas de abstractions y rechazo del adaptador `/typeorm` desde Domain/Application. El grafo complementa los selectores locales, incluyendo barrels.
- CPA-004: restricciones de Domain/Infrastructure/drivers e imports/reexports de archivos `.module`/`.module.js`/`.module.ts` para el transporte de Presentation. Los archivos `presentation/*/*.module.ts` se tratan como composición; ts-morph exige su nombre y ubicación correctos. Los archivos anidados no reciben esta selección de composición. El grafo complementa los imports locales con módulos alcanzables por barrels.
- Opciones literales `cascade: true`, cascadas con arrays no vacíos, `lazy: true`, `onDelete: 'CASCADE'` y eliminación de huérfanos en `persistence/schemas/`, `entities/` y `models/`.
- `synchronize: true` literal bajo `src/infrastructure/database/`.

Las directivas inline de ESLint están deshabilitadas y los warnings hacen fallar el comando. Una supresión no autoriza incumplir el catálogo. Estos selectores detectan sintaxis concreta: opciones calculadas, aliases de métodos, callbacks transaccionales y configuración construida dinámicamente requieren verificaciones adicionales y revisión. Un objeto con esos nombres en las carpetas ORM se interpreta como configuración de persistencia.

BCK-023 usa ts-morph para archivos hermanos y símbolos, y el grafo para dependencias de shared; ESLint no duplica esas comprobaciones. Sus selectores recursivos de Application siguen cubriendo todas las nuevas carpetas. La regresión de lint con tipos analiza los archivos Health en `application/health/get-health-check-objects/` con la configuración real.

### dependency-cruiser

[dependency-cruiser.config.mjs](../dependency-cruiser.config.mjs) verifica fuentes TypeScript antes de compilarlas, incluidos imports exclusivamente de tipos. Usa `tsconfig.json`, `exportsFields: ['exports']` y condiciones de tipos/ESM para resolver la entrada pública del workspace sin aliases a fuentes externas. Prioriza `types`/`typings` en manifests que no usan exports. Conserva dependencias externas visibles sin recorrer sus internals de `node_modules`.

Valida ciclos, imports irresolubles, dependencias de desarrollo desde runtime, fronteras entre capas y acceso a Node desde el núcleo. Domain/Application no pueden alcanzar Infrastructure, Presentation, configuración o composición mediante barrels intermedios. La lista de frameworks/proveedores reconocidos incluye NestJS, TypeORM, pg, React, Ionic, Capacitor y SDKs AWS/Azure; un proveedor nuevo requiere actualizar y probar esta detección.

La SPA elegida ahora es Angular/TypeScript y los proveedores aceptados están en [Infraestructura, proveedores y ambientes](../../../../../docs/architecture/infrastructure-providers.md). La lista anterior describe la detección implementada, no el stack frontend seleccionado. Angular y los SDKs Firebase/Google/Neon no se incorporan automáticamente a ese selector por esta decisión documental; BCK-008 sigue prohibiendo cualquier framework/proveedor en el núcleo. Antes de incorporar SDKs o ampliar cobertura se deben actualizar y probar los validadores afectados. Este gate no verifica infraestructura remota, workflows ni portabilidad Neon/Cloud SQL, y no certifica frontend. La SPA/kit tienen su [gate frontend propio](../../../../../tools/frontend-architecture/README.md), con reglas FRT y regresiones multiproyecto.

Los checks de capas se aplican a `src/domain/`, `src/application/`, `src/infrastructure/` y `src/presentation/`, incluidos database y configuración bajo Infrastructure. Los modelos relacionados pueden importarse dentro del mismo Domain y desde Application sin un `public.ts` por feature. La regla anterior `BCK-014-context-public-api` se retira conforme al ADR 0008. `AppModule` mantiene la composición raíz fuera del núcleo.

`BCK-023-shared-no-operations` rechaza dependencias estáticas alcanzables desde `application/shared/`, `application/ports/` y `application/<recurso>/shared/` hacia carpetas de operación. Incluye imports de tipos, aliases y reexports/barrels, y permite que operaciones consuman shared del recurso o transversal. [dependencies.test.ts](../test/architecture/dependencies.test.ts) ejecuta la configuración real sobre ambos sentidos del grafo. Imports dinámicos no resolubles y reutilización semántica conservan revisión.

CPA-004 reconoce composición por el path `presentation/<recurso>/<recurso>.module.ts`. Permite sus bindings hacia Domain/Infrastructure y mantiene las restricciones de imports directos de los demás archivos de Presentation. `CPA-004-transport-no-composition` impide que esos adaptadores alcancen archivos `.module.ts` de `src/`, incluso mediante barrels intermedios. Los módulos mal nombrados/anidados no reciben el permiso en el grafo y el gate de layout los rechaza. Domain/Application no alcanzan Presentation y Infrastructure no la importa. Regresiones positivas/negativas: [dependencies.test.ts](../test/architecture/dependencies.test.ts), incluidas aliases de Infrastructure, specifiers `.js`, imports de tipos y barrels.

CPA-002 permite el index público de CQRS y rechaza dependencias directas de Application hacia otros módulos de `libs/backend/cqrs/src/` o `dist/`. La resolución del paquete real se verifica con el gate sobre la API; las fixtures acreditan entrada pública y deep imports. Los imports internos del propio index siguen permitidos.

La API puede consumir librerías backend y contratos; no otra app, librerías cliente, tests ni herramientas. El análisis comienza en esta API: no acredita todas las dependencias del monorepo ni que una librería general carezca de negocio. La propiedad de tablas y ausencia de acceso SQL a persistencia privada de otras aplicaciones requieren revisión.

CPA-003 permite el index principal de abstractions y el index `/typeorm` desde Infrastructure. Rechaza módulos privados directos; BCK-008 impide que Domain/Application alcancen el adaptador transaccional mediante barrels, incluso si no importa un driver directamente. Fixtures y resolución real acreditan ambas entradas del workspace. El lint propio del paquete mantiene su entrada principal independiente de TypeORM/Node/proveedores.

BCK-008 también impide el adaptador `@casepilot/exception-handler/nestjs` en Domain/Application: ESLint rechaza imports/reexports directos y dependency-cruiser rechaza el directorio de su adaptador mediante dependencias alcanzables, incluyendo barrels. Los errores de la entrada principal pura de abstractions y sus reexportaciones de compatibilidad están permitidos. Regresiones: [eslint.test.ts](../test/architecture/eslint.test.ts) y [dependencies.test.ts](../test/architecture/dependencies.test.ts). El [lint de la librería](../../../../libs/backend/exception-handler/eslint.config.mjs), con [tests propios](../../../../libs/backend/exception-handler/test/unit/architecture.test.ts), protege su entrada pura (BCK-008): solo admite contratos locales y la entrada pública pura de abstractions, rechazando su adaptador TypeORM y deep imports. También rechaza imports de apps (BCK-015). La incorporación del adaptador de errores no modificó el catálogo normativo. El CRUD agrega handlers y repositorios y utiliza el contrato transaccional existente; su evidencia se describe abajo.

El [handler HTTP compartido](../../../../libs/backend/exception-handler/README.md) aporta evidencia de BCK-016 mediante [unitarias de normalización](../../../../libs/backend/exception-handler/test/unit/problem-details.test.ts) e [integración NestJS](../../../../libs/backend/exception-handler/test/integration/nestjs.test.ts). Verifican status/body Problem Details, errores síncronos/asíncronos, guards/pipes, routing y ausencia de causas/propiedades privadas en respuestas. [Abstractions prueba el contrato de errores](../../../../libs/backend/abstractions/test/unit/errors.test.ts) y [exception-handler verifica la identidad de sus reexportaciones](../../../../libs/backend/exception-handler/test/unit/errors.test.ts). La [prueba de composición API](../test/unit/error-handling.test.ts) verifica ambos modos y el mapeo estándar de UnexpectedError a Health 500 sin base; [la integración Health](../test/integration/health.test.ts) acredita el 500 ante PostgreSQL caído/tabla ausente, con mensaje genérico y stack cuando el detalle está habilitado, sin datos del driver. [Configuración](../test/unit/configuration.test.ts) prueba defaults, overrides, precedencia y booleanos inválidos de API_ERROR_DETAILS. `pnpm check:abstractions` y `pnpm check:exception-handler` ejecutan los checks de sus paquetes propietarios sin Docker. El contenido seguro de mensajes intencionalmente expuestos y el logging de cada consumidor siguen requiriendo revisión.

### ts-morph

[source-layout-rules.ts](../tools/architecture/source-layout-rules.ts) verifica los paths de las fuentes incluidas en el proyecto TypeScript, incluso archivos sin imports: BCK-014 exige las cuatro carpetas compartidas directamente bajo `src/`, sin `contexts/` ni capas repetidas; BCK-017 exige que las carpetas database estén directamente bajo Infrastructure. Admite archivos de bootstrap/composición en la raíz y no analiza tests ni archivos excluidos del proyecto. No determina semánticamente el contenido de un archivo mal nombrado ni la propiedad de tablas.

El mismo checker aplica CPA-001 a toda `src/application/`: requiere al menos una subcarpeta por recurso o responsabilidad lógica y rechaza carpetas llamadas `commands` o `queries` en cualquier nivel, sin distinguir mayúsculas. No usa una lista cerrada de recursos. Admite subcarpetas por operación y responsabilidades compartidas explícitas, como `ports/` o `shared/`. Comprueba la estructura de los paths, no la correspondencia semántica entre un archivo y su recurso.

[application-operation-rules.ts](../tools/architecture/application-operation-rules.ts) agrega BCK-023: cada recurso tiene carpetas de operación en kebab-case con los tres archivos directamente bajo ellas. Comprueba clases concretas exportadas en sus respectivos archivos, sin aceptar archivos vacíos, clases abstractas o reexports. Compara por declaración los modelos usados en `execute` con sus hermanos, admitiendo aliases del mismo símbolo y rechazando clases de igual forma declaradas fuera de la operación. No permite handlers ni requests concretos en shared/ports; sí bases abstractas de Request y datos compuestos de Response. Colaboradores exclusivos pueden permanecer en subcarpetas de la operación.

El checker identifica imports/reexports estáticos resolubles de colaboradores auxiliares entre operaciones y exige trasladarlos a shared; conserva la posibilidad de componer casos de uso mediante sus contratos explícitos Handler/Request/Response. El grafo protege shared también mediante dependencias alcanzables. [application-operations.test.ts](../test/architecture/application-operations.test.ts) cubre aceptación/rechazo, aliases, reexports, operaciones incompletas, nombres, alcance API/Application y todos los 141 handlers reales de los 29 recursos. Mueve solo en memoria una respuesta real para demostrar que la regla la selecciona. Los snippets en memoria usan las librerías ES2022, sin cargar DOM innecesariamente. Detectar duplicaciones, decidir qué datos/reglas se comparten y determinar el recurso propietario requieren revisión semántica; no se afirma certificación del monorepo ni de fuentes excluidas del proyecto.

CPA-004 exige que cada fuente de Presentation pertenezca a una carpeta con `<recurso>.module.ts` incluido en el mismo proyecto TypeScript. El módulo tiene que estar directamente en `presentation/<recurso>/` y coincidir con el nombre del recurso. Controllers `.controller.ts` fuera de Presentation y módulos `.module.ts` fuera de esa ubicación se rechazan, salvo AppModule/ApiModule raíz y módulos técnicos de Infrastructure. Permite subcarpetas de transporte del recurso, sin módulos anidados. [structure.test.ts](../test/architecture/structure.test.ts) acredita paths permitidos/rechazados, archivos sin imports, alcance local de la API y traslado en memoria del módulo Health real a su ubicación anterior. La existencia del archivo propietario no demuestra que sus metadata registren todos los controllers/providers ni que su contenido sea exclusivamente composición.

[use-case-rules.ts](../tools/architecture/use-case-rules.ts) analiza las clases en toda `src/application/`, incluidos recursos y subcarpetas de operaciones. Reconoce clases con sufijo `Command`, `Query` o `Handler`, además de clases que declaren `execute`. Los archivos `.command.ts`, `.query.ts` y `.handler.ts` deben declarar su handler; requests/responses y errores no se interpretan como handlers por compartir carpeta.

Para cada operación, el handler declara un método público de instancia `execute`, con un único parámetro explícito, requerido, de la clase concreta `<Operation>Request` de Application de esta app. No admite argumentos adicionales, defaults, rest ni sobrecargas. El retorno explícito es la clase concreta `<Operation>Response`, o `Promise` de esa clase, también en Application. Se admiten aliases de imports y tipos que resuelvan a esas clases; interfaces y clases abstractas no satisfacen el contrato.

CPA-002 requiere clases `<Operation>Handler` en archivos `<operation>.handler.ts` cuyo basename coincide con la operación convertida a kebab-case e implementación explícita de `Handler<Request, Response>` cuyo símbolo pertenece al paquete CQRS del workspace, en fuentes o declaraciones construidas. Los dos argumentos genéricos coinciden por símbolo con los modelos concretos de `execute`, que devuelve Promise. Acepta aliases de import, namespaces y reexports del mismo contrato; rechaza interfaces locales de igual forma, aliases locales especializados y contratos solo heredados.

Todas las clases con sufijo Request/Response en Application deben heredar de la base correspondiente real de CQRS, directamente o mediante clases intermedias. Las bases locales falsas no cumplen. Los tests aíslan las reglas BCK reutilizables, que permiten respuestas síncronas, de la restricción particular CPA-002, que exige Promise y los contratos compartidos. La suite verifica el Handler Health real y demuestra que quitar su cláusula implements produce una infracción.

También compara los símbolos reales de los retornos explícitos con la clase declarada: dos clases con igual nombre o forma no equivalen. Ignora retornos de callbacks internos. Inspecciona llamadas directas `handler.execute(...)` que el servicio de lenguaje puede asociar con el método y confirma la declaración resuelta del receptor antes de comprobar cantidad y tipo de argumentos. La regresión BCK-004 en [structure.test.ts](../test/architecture/structure.test.ts) acredita que handlers con firmas estructuralmente idénticas no se confunden y que un request de otra clase sigue rechazándose. Esta corrección conserva la normativa, ESLint y dependency-cruiser sin cambios. Emite errores como:

```text
src/application/cases/close-case.handler.ts:12: error BCK-004: ...
src/application/health/get-health-check-objects/get-health-check-objects.handler.ts:11: error CPA-002: ...
src/application/queries/read-case.query.ts:1: error CPA-001: Group Application files under src/application/<resource>/ ...
```

Este análisis no recorre todos los flujos de datos: llamadas indirectas/desestructuradas, adaptadores de bus, valores forzados mediante casts, instanciación real detrás de tipos estructurales e inputs/contexto verificado necesitan revisión o checks específicos. El gate nativo de TypeScript acredita la compilación y los retornos incompletos; el scanner no utiliza los diagnósticos de compilación de ts-morph, cuyos wrappers no preservan todos los formatos implícitos de módulos NodeNext.

### Repositorios y Unit of Work con ts-morph

[data-access-rules.ts](../tools/architecture/data-access-rules.ts) añade BCK-021/BCK-022 y CPA-003 al mismo gate. Selecciona todas las fuentes del `src/` de la API incluidas en TypeScript, aun sin imports: interfaces en `domain/repositories/`, clases en `infrastructure/persistence/repositories/`, declaraciones con sufijo Repository/UnitOfWork y herederos de los contratos reales. No recorre tests como fuentes de producto ni certifica otras apps/libs. El lanzador rechaza un proyecto vacío y [data-access.test.ts](../test/architecture/data-access.test.ts) acredita el repositorio Health real.

Resuelve los símbolos reales de Entity/Repository/CrudRepository/UnitOfWork y PageRequest/PageResponse desde fuentes/declaraciones del paquete del workspace. Inspecciona firmas públicas declaradas/heredadas, overloads y propiedades de función; deja fuera constructores técnicos y helpers privados/protegidos. Acepta primitivos, arrays/readonly arrays, Promise en retornos y genéricos con restricciones válidas. Rechaza objetos/DTOs/ORM, utilitarios de objetos, tuplas, intersecciones y modelos de igual forma sin herencia explícita; los items de PageResponse también se verifican. Los alias/reexports del mismo símbolo y la herencia indirecta son válidos. Las restricciones genéricas de TypeScript y el lint siguen siendo parte del gate.

Para UnitOfWork verifica contrato real y scope no vacío con propiedades de repositorio. Rechaza inyección/uso de UnitOfWork desde repositorios y llamadas directas a otros repositorios (BCK-009). Analiza callbacks literales y funciones/variables resolubles por símbolo: deben estar en Application, usar repositorios del parámetro de scope y evitar anidar UnitOfWork. Admite aliases locales y destructuring del scope. Callbacks/llamadas indirectos no resolubles, mutación posterior de aliases, escapes, cast del resultado, operaciones sin await y factories dinámicas conservan revisión manual; no se afirma análisis completo de flujos.

Las pruebas de comportamiento del [paquete abstractions](../../../../libs/backend/abstractions/README.md) verifican el mecanismo con PostgreSQL: commit/rollback entre dos repositorios, fallo durante commit, scopes concurrentes y paginación de una sentencia. Health conserva sus lecturas sin escrituras de producto. Las fábricas del CRUD acreditan el uso del manager transaccional, rollback y concurrencia mediante [integración](../test/integration/professional-services.test.ts); las nuevas fábricas deben aportar la misma evidencia. `pnpm check:abstractions` y `pnpm test:abstractions:integration` son comandos adicionales del paquete propietario, y el segundo requiere Docker/Testcontainers.

## Cobertura del catálogo

El CRUD agrega [unitarias directas de Application](../test/unit/crud.test.ts) y [pruebas HTTP/PostgreSQL](../test/integration/professional-services.test.ts) para los 28 recursos. Acreditan selección explícita de campos, scopes por cuenta, integridad de referencias incluso ante un resultado de repositorio ajeno a la cuenta, versiones, conflictos, rollback, precisión y compatibilidad schema/migración. ## Pruebas y mantenimiento

Las suites [test/architecture/](../test/architecture/) son propias de esta API. Ejecutan ESLint sobre snippets, dependency-cruiser real sobre proyectos temporales y ts-morph sobre proyectos en memoria y fuentes reales sin guardarlas. Cubren relaciones de Domain permitidas, capas compartidas, database/configuración en Infrastructure, rechazo de contexts/capas repetidas, agrupación de Application por recurso/operación y trío obligatorio, aliases, imports de tipos, barrels, ciclos entre recursos, dependencias de desarrollo, firmas inválidas, modelos concretos, símbolos distintos y supresiones. Los fixtures de ESLint/dependency-cruiser usan recursos para acreditar que sus selectores de Application siguen aplicando en subcarpetas. Una regresión modifica solo en memoria el handler Health real en `application/health/get-health-check-objects/` para acreditar que el scanner lo selecciona y que el layout rechaza su ubicación anterior; la suite BCK-023 acredita todas las operaciones reales. Los proyectos temporales se crean bajo `build/` y se eliminan validando su pertenencia a esa carpeta; no modifican las fuentes ni los recursos locales de desarrollo.

El procedimiento para agregar, modificar o retirar reglas y ampliar su cobertura está en la [skill architecture-rules-sync](../../../../../.agents/skills/architecture-rules-sync/SKILL.md). Coordina catálogo backend, guía base, monorepo y adopción con los checks afectados, sus ejemplos válidos/inválidos y esta matriz. Revisa documentación → ejecución y ejecución → documentación, conservando la evidencia adicional que cada regla requiere. Los comandos y límites propios de esta API mantienen su fuente en este documento.

Versiones fijadas: ESLint 9.39.5, typescript-eslint 8.71.0, dependency-cruiser 18.5.0 y ts-morph 27.0.2. ts-morph incluye TypeScript 5.9.2 para análisis; la API compila con TypeScript 5.9.3. Se conserva la misma familia de compilador y se prueban resoluciones/símbolos. Las nuevas herramientas tienen licencia MIT y uso exclusivo de desarrollo, sin añadir peso al runtime ni a web/Capacitor. dependency-cruiser declara soporte Node `^22 || ^24 || >=26`; revisar engines y compatibilidad al actualizar las herramientas.
